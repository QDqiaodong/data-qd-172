# Alert aggregation contract

Each observation has a unique ID, sensor ID, UTC timestamp, latitude, longitude, and severity score from 0 through 1. Two observations are adjacent when their timestamps differ by at most the configured number of minutes and haversine distance is within the configured radius. Connected components form candidate incidents; this transitive rule can create clusters whose endpoints exceed the radius. Incident ID is the lexicographically smallest observation ID. Confidence is the number of distinct sensors divided by observations, alongside the raw count. This is alert triage, not a fire boundary or emergency dispatch decision.

Optional `maintenance_windows` list planned sensor outages as `sensor_id`, `start`, `end` with offset-bearing timestamps; `start` must precede `end`. An observation whose timestamp falls in the half-open interval `[start, end)` of any window naming its exact sensor ID is suppressed: it appears only in `suppressed_observation_ids` (sorted lexicographically) and contributes no vertex, edge, sensor count, observation count, confidence, or mean severity to any incident, so it cannot bridge two incidents. Windows may overlap or repeat without extra effect, and they never affect other sensors. The top-level `observation_count` still counts every input observation, suppressed or not.
